# wilkr

Personal, self-hosted, segments-first fitness platform.

## Quickstart

```
cp .env.example .env        # then edit the password
docker compose up --build
docker compose exec api alembic upgrade head
curl http://localhost:8000/health
```

That's the whole Phase 0 skeleton — no auth, no business logic yet, just a
tailnet-reachable API with the full schema applied. Migrations are not
auto-run on container start; running `alembic upgrade head` is a deliberate,
observable step.

## Layout

- `docs/` — planning docs (charter, context, ERD). Filenames still carry the
  project's original working title, "OpenFit"; content is otherwise current.
- `schema/` — the schema as DBML (`wilkr.dbml`, hand-editable source of
  truth) and its generated PostgreSQL DDL (`wilkr.postgres.sql`). View the
  diagram by pasting `wilkr.dbml` into [dbdiagram.io](https://dbdiagram.io).
- `app/` — FastAPI application (`app/models/` mirrors `schema/wilkr.dbml`
  table-for-table; kept in sync by hand, not autogenerated from it).
- `migrations/` — Alembic. `migrations/versions/0001_initial_schema.py`
  executes `schema/wilkr.postgres.sql` verbatim, statement by statement, so
  the reviewed DDL (corrected FK directions, `CHECK` constraints, unquoted
  PostGIS geometry types) is what actually gets applied.

## Verifying a fresh clone

After the Quickstart above:

```
docker compose exec api alembic revision --autogenerate -m "sync check"
```

This should produce an **empty** migration (no `op.` calls) — proof the
hand-written models in `app/models/` exactly match the schema the migration
applied. Delete the empty revision file after confirming. If it isn't empty,
the diff it shows is the discrepancy to fix in `app/models/`.
